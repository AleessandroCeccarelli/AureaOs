# AureaOS Application and Component Catalog

This is the authoritative inventory of named first-party applications, desktop components, system tools, services, and shared design resources found in AureaOS documentation. It records direction and status; it is not a statement that planned software exists.

## Platform and status

AureaOS Roma 1.0 targets Debian GNU/Linux 13 (Trixie), `amd64` (x86-64). AureaOS is GUI-first and Wayland-first. The repository has an early, terminal-only Debian root filesystem bootstrap and design resources. No AureaOS desktop UI or first-party application is implemented.

Status labels:

- **Implemented foundation:** documentation, design resources, or other groundwork exists; the named application or complete component is not implemented.
- **Planned:** included in the current product direction. “Roma 1.0 priority” below reflects current roadmap/product documents, not a delivery commitment.
- **Candidate:** documented concept or earlier project name whose scope or continued use is not confirmed.
- **Undecided:** no settled product or technical choice is documented.

Rust is the primary programming language for AureaOS applications and components where appropriate. A non-Rust choice requires a documented technical reason. It is not a requirement for third-party software, visual assets, or web styling such as CSS. No UI toolkit has been selected. Vulkan remains a candidate, not a confirmed rendering choice.

## Shared UI and language contract

All first-party desktop and system applications should follow [AureaOS Human Interfaces](../human-interfaces/README.md), including shared semantic design tokens, light and dark themes, typography, spacing, controls, icons, and interaction patterns. The current CSS token set is the source of truth for implemented web-theme values; native toolkit mappings should consume the same semantic contract rather than create competing palettes. Reusable cross-toolkit UI components are not implemented.

Use Aurea Sans as the primary typeface direction, with readable fallback fonts. The final font selection and fallback stack remain open. Interfaces must support keyboard navigation, visible focus, accessible labels and feedback, scalable text, and reduced-motion preferences. Use consistent product names and plain-language copy. App layouts may differ to suit their tasks while retaining AureaOS visual and linguistic identity.

The default UI language and localization policy have not been established and remain open decisions.

## Scope notes

The current Roma 1.0 direction includes the desktop foundation, shared design work, core system applications and the three system tools labeled “planned for Roma 1.0” above. Their scope and implementation remain subject to development and validation. Sonus, Visio, Explora, Aurea Greeter, Aurea Media API, Aurea Wallet, system-level passkeys, and Aurea AI/ChatGPT integration are candidates or exploratory ideas, not Roma 1.0 commitments. Aurea Time is the single planned system for backup and restore, including full-system restore; Btrfs's native snapshot workflow is not part of the design.

Update domains remain distinct: Debian base packages, AureaOS-specific system components, and Flatpak applications. The mechanisms for the first two channels are not yet implemented.

| **Aurea Fixed Refresh** | System service / display strategy | Descriptive project name. | Select a suitable supported fixed refresh mode when VRR is unavailable or unsuitable. | Planned; part of Aurea Display Intelligence. | Rust primary where appropriate. | DRM/KMS mode setting through the selected graphics driver; policy and safe fallback behavior are to be implemented. | Automatic fallback and manual fixed-rate selection in Display & Video settings. |
| **Display Policy Engine** | System service | Functional name. | Choose per-display resolution and refresh policy using hardware capabilities, frame cadence, desktop context, power policy, and user preferences. | Planned; part of Aurea Display Intelligence. | Rust primary where appropriate. | Policy module integrated with display capability discovery and the DRM/KMS backend; exact service API remains open. | Provides the Automatic — AureaOS behavior and respects manual overrides. |

These display components are architectural modules within Aurea Display Intelligence, not five separate applications or independent daemons by default. Their final process boundaries will be decided during implementation. VRR and fixed-refresh strategies must be able to operate independently on different monitors in a multi-display setup.

The compositor supplies output lifecycle and presentation information and coordinates changes, but it must not become the owner of the entire display policy. DRM/KMS and the graphics driver expose and apply hardware capabilities; AureaOS owns the policy and user experience. No universal VRR range or minimum refresh rate is assumed.
